0. 文档说明 #
0.1 文档目的 #
本 PRD 定义一套跨产品 A/B 实验平台。平台支持多套实验并行运行，并保证用户分组稳定、实验曝光可追溯、指标口径一致、结果能够复核、异常能够停止和恢复。
第一阶段是本 PRD 的承诺范围，目标是建立可信的基础实验闭环。第二阶段为 conditional_on_phase_1_learnings ，只有第一阶段通过验收、试点实验能够稳定产出可信结论后，才进入独立评审和排期。

0.3 术语 #
术语
定义与例子
subject
随机分组的业务主体。Phase 1 默认使用当前产品内可稳定识别的玩家账号；同一玩家重复访问时仍归属同一实验组。
assignment
平台为 subject 计算实验与 variant 的决策记录。用户被分组但未进入相关页面时，只有 assignment ，没有 exposure 。
exposure
用户真正受到实验变化影响的事件。例如用户被分到新版充值页，但未打开充值页，不算曝光。
analysis_population
预先定义的统计人群。默认使用 intent_to_treat ，即纳入全部合格且已随机分组的主体；只有触发条件发生在实验影响之前、且两组口径一致时，才使用 triggered 人群。失败例：新版页面更容易加载成功，却只分析加载成功者，会把 Variant 造成的加载差异从样本中删掉。处理方式：回到 assignment 人群分析，并把曝光完整性列为诊断指标。
control
代表当前线上基准体验的实验组。
variant
需要验证的新体验或新参数。Phase 1 每个实验只支持一个 control 和一个 variant 。
layer
允许并行实验的业务层。例如 Lobby UI 与消息触达属于不同 layer ，用户可以同时参加。
mutex_group
必须互斥的实验集合。例如两个都修改首页排序的实验不能让同一用户同时命中。
factorial_cell
受控 2×2 试点中的一个组合单元。例如“美术 Variant + RTP Control”。四个组合单元用于分别估计两个实验的主效应和交互风险。
interaction_effect
一个实验的效果随另一个实验组别发生变化。例如新美术只在 RTP Variant 下提升，但在 RTP Control 下无效。
concurrent_assignment_set
同一 subject 在同一结果窗口内生效的全部实验分组集合，用于追踪跨层实验叠加。
SRM
Sample Ratio Mismatch，实际样本比例与预设比例出现非随机偏差。失败例：预设 50/50，实际长期为 58/42。处理方式：暂停结论，排查分桶、曝光和数据链路。
guardrail_metric
防止局部指标提升却伤害整体业务的护栏指标。例如转化率提升，但净收入、性能或投诉指标明显变差。
MDE
Minimum Detectable Effect，实验计划检测的最小业务效果。Phase 1 由实验负责人和数据负责人共同填写，平台暂不自动计算。
holdout
长期不进入某类优化的对照用户，用于衡量多个迭代的累计影响。该能力属于 Phase 2。
kill_switch
紧急停止实验新增影响的能力。例如护栏越界后，后续决策回到安全基准，同时保留已产生状态和审计记录。
0.4 产品类型与边界 #
本产品以 data_analytics 为主，兼具 b2b_saas_ops 工作流。它提供实验创建、审核、流量治理、数据质量监控、统计分析和决策记录，不负责决定底层技术栈、部署方式、供应商、商业价格、团队编制或各司法辖区的具体合规结论。
1. 摘要 #
1.1 背景 #
历史方案已经提出建立核心指标、实验分流、统计分析、监控告警和自助实验平台，并计划先通过 2–5 个核心游戏场景跑通流程。现有材料还记录过 SS03 调整实验流量、增加新数学表测试组的实际需求，说明团队已经需要管理真实实验。
当前材料尚未形成一份覆盖并行实验治理的完整产品契约。以下能力缺口会直接削弱实验可信度：
同一用户是否稳定进入同一组没有统一约束。
获取配置和真正曝光容易混为一谈。
多套实验并行时缺少 layer 和互斥规则。
缺少统一的指标版本、SRM 检测、停止规则和结果决策标准。
扩量、暂停、回退和审计依赖人工沟通，风险不可控。
1.2 产品目标 #
Phase 1 建立一套可审计的基础闭环，使获授权的产品、运营、数据和工程角色能够：
创建一个包含假设、受众、变量、指标、周期和负责人信息的实验。
稳定地把符合条件的用户分入 control 或 variant 。
在用户真正受到影响时记录 exposure 。
监控流量比例、数据质量、主指标和护栏指标。
按预先约定的固定周期给出可复核的实验结果。
管理多套并行实验的 layer 、互斥、灰度扩量和紧急停止。
对一组指定的“美术素材 × RTP/调控机制”二元实验运行受控 2×2 试点，识别两项改动的独立效果和明显交互风险。
第 7 项是 Phase 1 的限定试点，不代表平台已支持任意数量实验的自动交互检测。
1.3 核心成功定义 #
Phase 1 以以下可验证结果验收：
至少 2 个不同场景的试点实验完成从创建到结论的闭环；具体场景由立项评审确认。
试点实验没有未解释的严重 SRM、跨组或曝光口径问题。
每个结论都能回溯到实验版本、分组、曝光、指标版本和决策记录。
指定 2×2 试点的四个组合单元都能追溯到双实验分组和各自曝光，且结束时没有未解释的联合 SRM。
紧急停止演练能够让新增曝光回到安全基准，并保留完整审计记录。
产品和数据负责人能根据统一规则得出相同的 ship 、 extend 、 stop 或 investigate 判断。
1.4 失败与退出标准 #
出现以下任一情况，Phase 1 不进入规模化建设：
试点实验无法稳定识别随机主体，导致用户频繁换组。
曝光事件无法与结果事件可靠关联。
关键指标在相同数据窗口下无法重复计算出一致结果。
严重 SRM 发生后无法定位原因或阻止错误结论。
平台没有减少实验配置、核对和出报告的人工工作。
即使业务指标没有出现正向提升，只要平台能够证明某个方案无效、识别一次错误分流或阻止一次负向发布，也视为有效学习；但这不替代上述数据可信度验收。

2.2 用户价值主张 #
平台把一次实验从“临时分流 + 人工拉数”变成可重复的产品流程。每个实验都有明确假设、稳定分组、真实曝光、统一指标、数据质量状态和结论记录。
2.3 产品原则 #
可信优先于速度 ：数据质量不通过时，结果页不得给出胜负结论。
先锁定计划，再观察结果 ：主指标、周期和停止规则在实验开始前冻结。
分析人群提前锁定 ：默认使用 intent_to_treat 。只有触发条件早于实验影响且两组口径一致时，才使用 triggered 人群； exposure 用于证明实验是否真正触达和诊断链路。
安全基准始终存在 ：实验异常时可回到 control 或已批准的安全配置。
并行不等于无约束叠加 ：冲突实验必须互斥，跨层实验需要保留交互风险记录。
平台给出证据，不替代负责人决策 ：自动化建议不自动发布到全量。

3.3 试点场景选择原则 #
Phase 1 应选择至少两个风险和反馈周期不同的场景：
一个低风险、结果较快的体验类场景，例如 Lobby UI、加载页或文案。
一个业务价值较高、需要护栏和审批的机制类场景，例如 Bonus 参数或游戏配置。
当试点同时包含美术素材和 RTP/调控机制时，默认使用两个不同 layer ： art_presentation 与 player_value_intervention 。纯展示型素材可以作为普通跨层实验并行；会改变价值感知或游戏操作反馈的素材，必须进入受控 2×2 试点或改为顺序测试。
试点不以“容易做出正向结果”为选择标准。优先选择能够验证分桶、曝光、指标、互斥和停止能力的场景。

4.3 结果评审流程 #
系统确认实验达到固定周期和最低样本条件。
数据质量检查确认 SRM、曝光完整性、事件延迟和指标版本正常。
结果页展示主指标、护栏指标、效果区间和实际样本。
产品负责人和数据负责人按照附件决策指南记录结论。
ship 进入灰度全量； extend 形成新的结束条件； stop 回到基准； investigate 保持非全量状态并记录待解决问题。

5.4 assignment 与 exposure #
平台分别记录决策和真实曝光，不能用配置请求代替曝光。统计人群由 analysis_population 预先锁定，曝光记录不能在看到结果后用来任意筛选样本。
验收标准：
control 和 variant 使用同一曝光触发口径。
同一曝光可识别重复上报，重复不增加实验样本。

intent_to_treat 实验以合格且已分组主体为分析人群；没有曝光的 assignment 仍进入主分析，并通过曝光指标解释触达差异。
triggered 实验只有在触发条件发生于实验影响之前、且两组触发口径相同时使用；条件不满足时回到 intent_to_treat 。
延迟或补发事件保留原始发生时间和接收时间。
并行实验分别生成独立 assignment ；结果事件能够关联当时生效的 concurrent_assignment_set 。
美术素材与 RTP/调控机制分别定义和上报 exposure ，不能用其中一个实验的曝光代替另一个。
5.5 指标管理 #
每个实验必须选择一个 primary_metric ，并选择至少一个与风险相关的 guardrail_metric 。指标定义包含公式、单位、统计主体、分析人群、分析方法、窗口、数据源、刷新频率、版本和负责人。
指标一旦随实验启动冻结，修改定义必须形成新指标版本，并由数据负责人判断：
原实验继续使用旧版本；或
当前实验因口径失效而终止，使用新版本重新开始。
具体指标模板见 [[02-Projects/Active/A-B实验平台/audience/A-B 实验平台 - 指标字典.md]]。

数据状态不是 invalid
没有未解释的严重 SRM
护栏指标未触发停止条件
当前版本通过对应 QA
上一阶段达到最短观察条件
紧急停止后：
新的决策返回安全基准。
停止原因、操作人、时间、影响范围进入审计记录。
已产生的 Bonus、订单、投注或其他业务状态不被自动删除。
恢复需要新的批准记录，不能自动回到原流量。
5.10 Phase 2 产品能力 #
Phase 2 的九项能力沿用 §3.2 的进入条件。每项独立补充产品需求和统计评审，不在 Phase 1 中预埋不可验证的复杂配置。
Feature Flag 与实验统一时仍保留概念边界：Flag 管理功能可用性，实验管理假设、随机分配、指标和结论。实验胜出后可以转为普通 Flag 灰度全量，但 Flag 打开本身不代表实验成功。

6. 交互与设计要求 #
6.1 信息架构 #
Phase 1 至少包含以下产品页面：
实验列表：状态、负责人、产品、 layer 、流量、周期、数据健康和结论。
实验创建页：假设、受众、变量、指标、周期、互斥、扩量与停止规则。
实验详情页：配置版本、运行状态、流量、事件健康、并行分组、结果和审计记录；受控 2×2 试点显示四个组合单元。
冲突视图：显示同一 layer 、 mutex_group 和潜在交互实验。
数据质量视图：SRM、曝光完整性、事件延迟、重复率和指标版本。
指标目录：指标定义、版本、负责人和可使用状态。
6.2 关键交互原则 #
风险状态不能只依赖颜色，必须有文字和原因。
所有比例同时显示百分比和实际样本量。
未到固定周期时，结果页不使用“胜出”“失败”等结论性文案。
扩量和紧急停止前显示影响范围、当前版本和后续状态。
互斥冲突必须列出冲突实验，不使用笼统的“配置错误”。
to_be_confirmed 指标或规则不能被误显示为已批准。
2×2 试点同时显示四个组合单元的目标比例、实际样本、双曝光完整性和数据健康；不能只展示两个单实验汇总结果。
6.3 可访问性与审计可读性 #
核心状态具有清晰文本标签。
表格支持复制和导出，导出内容保留实验版本与生成时间。
审计记录按时间排序，能区分配置修改、审批、扩量、暂停和结论。
7. 业务价值与投入逻辑 #
7.1 价值模型 #
平台价值来自三类结果：
减少负向发布：在小流量阶段发现护栏恶化并停止。
提高资源分配质量：让后续研发投入基于实验结果，而不是只依据观点。
降低重复劳动：复用分流、曝光、质量检查和报告流程。
7.2 Phase 1 投入原则 #

8. 合规、隐私与风险 #
8.1 风险原则 #
实验不能绕过现有的资金、Bonus、游戏数学、责任博彩、风控或用户权益审批。
受众条件只使用已批准的业务标签。敏感属性、推断属性和高风险定向需要独立合规确认。
日志和导出遵循现有数据访问权限，不因实验平台扩大可见范围。
安全修复、法规要求和明确 Bug 修复不应为了保留对照组而延迟。
具体司法辖区结论不在本 PRD 范围；相关实验上线前由合规角色确认适用政策。

9. 产品级技术约束与集成契约 #
本节只描述产品需要的语义，不规定服务、数据库、缓存、队列、SDK、云资源或部署拓扑。
9.1 决策契约 #
业务侧能够获得以下语义信息：实验标识、配置版本、组别、决策标识、配置参数、命中或未命中原因、是否处于降级状态，以及当前主体允许业务使用的 concurrent_assignment_set 。
决策过程需要满足：
对同一主体保持稳定。
在实验暂停或异常时返回安全基准。
在合理的业务响应时间内完成；具体阈值由工程评审确认。
支持测试身份验证指定组别，但测试覆盖不能污染生产分析。
9.2 事件契约 #
assignment 、 exposure 、结果事件和护栏事件必须能够通过实验、版本、组别、主体和时间关联。并行实验的结果事件还必须关联当时生效的 concurrent_assignment_set ，同时保留每个实验独立的曝光状态。事件重复、迟到和缺失都能在数据质量视图中识别。
9.3 身份约束 #
2026-05-20 的会议记录指出 OneID 短期不具备实施条件，当前维持现有用户 ID 体系。因此 Phase 1 不依赖跨产品统一身份落地。每个试点必须明确 subject_type 、稳定范围和身份冲突处理方式。
跨产品长期 Holdout、跨设备一致性和跨产品交互分析需要更稳定的身份能力，进入 Phase 2 前重新评估。
