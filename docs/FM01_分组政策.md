# FM01 玩家分组政策（2026-07-30 版）

> 适用游戏：FM01（捕鱼大师）· 数据表：`transform-agfish-game.public.bullet`
> 生效变更：**2026-07-30 16:00 PST**（= 2026-07-31 00:00 UTC）个性化挽留系统一期上线，分组逻辑随之更新。
> 本文为唯一分组口径索引，供取数 / 分析 / 报告统一引用。

---

## 0. 一句话

分组是**记录级（逐发子弹）判定**，按下述**优先级从上到下**匹配，命中即止：
**Dynamic RTP → 风控 → 个性化挽留 → default**。前三组由 `strategy_name` 决定，
最后两组由「时间 ≥ 7/30 16:00 PST + `user_id` 尾号」拆分。

---

## 1. 五个分组的定义与判定优先级

| 优先级 | 分组 | 判定条件（对每条 bullet 记录） |
|---|---|---|
| 1 | **Dynamic RTP 组** | `strategy_name = 'DYNAMIC_RTP_V3'` |
| 2 | **风控组** | `strategy_name LIKE 'RC_FISHING\_%'`（渐进钳制 L1–L4） |
| 3 | **风控组** | `strategy_name LIKE '%RISK_CONTROL%'`（即 `RISK_CONTROLLED`，直接高危） |
| 4 | **个性化挽留组** | 不满足 1–3，**且** 事件时间 ≥ `2026-07-30 16:00 PST`（=`2026-07-31 00:00 UTC`）**且** `user_id % 10 IN (0,1)` |
| 5 | **default 组** | 不满足 1–4（即剩余记录：上线前的剩余，或上线后尾号非 0/1） |

> 优先级必须严格从上到下：先看 `strategy_name`（1–3），落不到再用「时间+尾号」（4–5）。
> 风控组是 2、3 两条的并集。

## 2. 权威判定 SQL（可直接用于取数）

```sql
CASE
  WHEN strategy_name = 'DYNAMIC_RTP_V3'              THEN 'dynamic_rtp'
  WHEN strategy_name LIKE 'RC_FISHING\_%' ESCAPE '\' THEN 'risk_control'
  WHEN strategy_name LIKE '%RISK_CONTROL%'           THEN 'risk_control'
  WHEN event_timestamp >= '2026-07-31 00:00:00'   -- UTC, = 2026-07-30 16:00 PST 挽留上线
       AND user_id % 10 IN (0, 1)                    THEN 'retention'   -- 个性化挽留
  ELSE 'default'
END AS group_tag
```

## 3. 关键口径说明

- **尾号 = `user_id % 10`**（十进制末位）。末位 {0,1} ≈ 全量 20%，是天然均匀哈希，
  确定性、可复算、新玩家自动归组、终身不变。
- **时间戳口径**：分界点 **2026-07-30 16:00 PST = 2026-07-31 00:00 UTC**。用 `event_timestamp`（UTC）
  直接比 `'2026-07-31 00:00:00'` 即可（无需转时区）。若系统实现改用 `created_at`，需对齐同一字段。
- **上线时点即分界**：此前的"剩余"记录（尾号 0/1 也算）全部归 **default**（挽留系统尚未上线）；
  此后剩余记录才按尾号切 挽留 / default。数据显示 7/30 23:10 UTC 起有小规模灰度（13 玩家），
  7/31 00:00 UTC 起全量生效。
- **CR_FISHING_* 属于个性化挽留组**：数据里存在 `CR_FISHING_V1:T1~T4:P1/P2`（挽留系统的
  执行策略，T1–T4=生命周期层、P=奖池档）。它**不匹配** Dynamic/风控规则，落入"剩余"，
  再由尾号归组——已验证上线后 **CR_FISHING 玩家 100% 为尾号 0/1**（见§5），故必然、
  且应当归入个性化挽留组，规则自洽，无需额外条款。
- **挽留组的 strategy_name 组成**：加成时为 `CR_FISHING_V1:T*:P*`，未加成/兜底时为
  `DEFAULT_FALLBACK`——两类记录只要（上线后 + 尾号 0/1）都归挽留组。
- **一名玩家可跨组**：因判定是记录级，同一玩家不同时刻被不同系统接管的记录分属不同组；
  按玩家汇总时需先按 `group_tag` 聚合。

## 4. 各组当前量级（挽留上线后，记录级快照）

| 分组 | 主要 strategy_name | 记录数级别 |
|---|---|---|
| Dynamic RTP | `DYNAMIC_RTP_V3` | ~1,610 万发 / 4,264 玩家 |
| 风控 | `RC_FISHING_V1:1/4`、`RISK_CONTROLLED` | ~20 万发 / 200+ 玩家 |
| 个性化挽留 | `CR_FISHING_V1:T*:P*` + `DEFAULT_FALLBACK`(尾号0/1) | ~1,020 万发 / ~2,600 玩家 |
| default | `DEFAULT_FALLBACK`(尾号非0/1) | ~2,800 万发 / 8,369 玩家 |

## 5. 数据验证记录（2026-08-12 核对）

- CR_FISHING 全期最早记录 = **2026-07-30 23:10 UTC（≈7/30 15:10 PST）**，与上线时点吻合；
  23:10–24:00 UTC 为小规模灰度（13 玩家 / 9,573 发）。
- 分界（7/31 00:00 UTC）后 `CR_FISHING_` 尾号分布：尾号0 = 1,773 人、尾号1 = 1,757 人，
  **其他尾号 0 人** → CR_FISHING 100% 为挽留组玩家，确认归入挽留组。
- 上线后已无 `BOOST_POOL` / `DYNAMIC_RTP`(v1) / `DYNAMIC_RTP_V2` 记录（旧策略已停用）；
  若历史回溯遇到，按"非 v3 → 落入剩余/风控规则"处理。

## 6. 与旧版分组的差异

| 维度 | 旧版 | 新版（7/30 16:00 PST 起） |
|---|---|---|
| 挽留组进组 | `strategy='default' AND user_id%10 IN (0,1)` | 剩余记录 **+ 时间≥7/30 16:00 PST + 尾号0/1** |
| 时间条件 | 无 | 新增 **7/30 16:00 PST 上线分界** |
| 风控组 | 仅 RC_FISHING | RC_FISHING **∪ RISK_CONTROLLED** |
| Dynamic 组 | v1/v2/v3 | 仅 **v3**（v1/v2 已停用） |
| 挽留执行策略 | （设计阶段） | 实际以 `CR_FISHING_V1:T*:P*` 落库 |
