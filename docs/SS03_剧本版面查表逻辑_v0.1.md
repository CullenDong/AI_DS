# SS03 剧本版面查表逻辑 · v0.1

> 目的：把 Redshift 每一发 spin 对应到剧本库 v2_6 的剧本，取该剧本的**版面属性**（scatter 数、级联 steps、wild/golden 数量与使用数等），用于结合玩家数据做综合分析。本文只讲**查表（mapping）逻辑**，是所有剧本版面分析的地基。

## 0. 一句话

`Redshift snapshot.script_id` **不能直接**等于 catalog 的 uuid（uuid5 方案的表根本对不上）——必须先用 **`script_id_map.json`** 把 `script_id` 映射到**记录 uuid**，再用 **catalog** 拿版面属性。**map 负责 id 映射，catalog 负责版面字段**，两个文件各司其职。

## 1. 三个数据源

| 数据源 | 位置 | 提供什么 |
|---|---|---|
| **剧本库 catalog** | `data/input/SS03_MathTable_Database_v2_6/{BG,FG}_catalog.json` | 按 payout 桶索引每个剧本，键含 `uuid` + 版面属性 |
| **剧本文件** | `.../{BG,FG}_ReelSets/{payout}/{payout}_{id}.json` | 单剧本完整内容（`Reel_Sets` 转轮带版面等）；catalog 不够时才读 |
| **id 映射** | `.../script_id_map.json`（255MB） | `script_id ↔ 记录 uuid` 官方映射（本文的核心） |
| **玩家 spin** | Redshift `slot-machine`(5443) `public.fct_bet_orders` | 每发 `snapshot`（SUPER）含 `table_id`/`script_id`/实际盘面 |

> 只覆盖 **4 月后的新版本数据**。老数据（2 月–3/5）schema 不同，见 §6。

## 2. 为什么不能直接 join：两种 key_scheme（按表定，不是按时间）

每张交付的数学表把它的剧本条目按**某一种方案**编号（`script_id_map.json` 的 `tables[<表>].key_scheme`）：

| key_scheme | script_id 是什么 | 用这方案的表（共 13 raw / 10 uuid5） |
|---|---|---|
| **`raw`** | = 记录 uuid 本身（catalog 里能直接查到） | `normal_zero`/`go`/`ichi`/`ni`/`san`/`shi`/`roku`/`risky`/`kakuteiA/B/C`/`zero98kai`/`zero98kaini` |
| **`uuid5`** | = `uuid5(NAMESPACE_DNS, 记录uuid)`，**catalog 里查不到** | `zero_95_kai`、`BG97_Saitekika`、`BGTR95/97_Saitekika_*`、`BGTR95_HMM_Highvalue_v1`、`zero93kai`、`FGibento_lvl1/2/3` |

- 所以同一时间不同表会同时出现两种写法；"6 月起 v5 变多"其实是**流量转向了 uuid5 方案的表**（95kai/BGTR 系），不是时间切换。
- `uuid5` 是单向哈希（SHA-1），**数学上不可逆**，只能查表还原 → 这正是 `script_id_map.json` 的用途。虽然经验上 `uuid5(DNS, 记录uuid)` 能重算，但**以官方 map 为准**，不要自己重算（防边界情况）。

## 3. 查表逻辑（核心，逐步）

### 3.1 script_id → 记录 uuid（用 `script_id_map.json`）

```
输入: sid = snapshot.script_id
if sid in map["by_uuid"]:            # raw 方案：script_id 本身就是记录 uuid
    record_uuid = sid
elif sid in map["by_script_id"]:     # uuid5 方案：反查
    record_uuid = map["by_script_id"][sid][0]   # 每个 script_id 恰好对一个记录(官方保证)
else:
    未命中 → 该剧本不在 v2_6 库（例如库外的更新剧本）
```

`map` 结构：
- `by_uuid[记录uuid]` = `{records:[{side,payout,file_name,status}], script_ids:[uuid5], used_in:[{table,script,key_scheme,script_id}]}`
- `by_script_id[uuid5]` = `[记录uuid]`
- `tables[表名]` = `{key_scheme, scripts:{base.script, free.script}}`
- `used_in` = **剧本 → 用到它的表**（做"设计侧"分析时用它列出每张表的剧本集）

### 3.2 记录 uuid → 版面属性（用 catalog）

catalog 每条 = 一个剧本，键为记录 uuid，取以下字段：

| 字段 | 含义 |
|---|---|
| `side` | BG（基础游戏）/ FG（免费游戏） |
| `payout` | 该剧本总赔付（分桶键） |
| `steps` | 级联（cascade）步数 |
| `scatter_count` | 版面 scatter(201) 符号数 |
| `free_triggered` | 免费触发（0=无，10=base，12/14…=额外） |
| `total_wild` / `used_wild` | wild(202) 总数 / 参与中奖的 wild 数 |
| `total_golden` / `used_golden` | golden(100-108) 总数 / 参与中奖的 golden 数 |

> 符号编码：`201`=scatter，`202`=wild，`100-108`=golden，其余整数=普通符号，`-1/0`=空位。
> catalog 只有上述聚合属性；要完整转轮带版面（每列符号排布）时读剧本文件的 `Reel_Sets`，路径 `<side>_ReelSets/<payout>/<file_name>`。

### 3.3 合并成一张索引（一次烘好，反复用）

把「记录 uuid → 版面属性(catalog)」和「script_id → 记录 uuid(map，raw+uuid5 两方案)」合并为 **`script_id → 版面属性`** 一张表：

```
catalog:  记录uuid → 版面属性(side,payout,steps,scatter_count,free_triggered,
                               total_wild,used_wild,total_golden,used_golden)
map:      by_uuid 的每个记录uuid(=raw script_id) 与 by_script_id 的每个 uuid5 → 记录uuid
合并:     script_id(raw 和 uuid5 都收) → 版面属性
```

**产物**：`data/output/ss03_reelset_layout_index.parquet`（约 108MB，142 万行 = raw 742,906 + uuid5 742,906；列 `script_id/scheme/record_uuid/side/`+版面 8 字段）。
生成/使用脚本：`jobs/ss03_analysis/reelset_layout_lookup.py`。

## 4. 拿它分析玩家数据

从 Redshift 取 spin（`snapshot.table_id`、`snapshot.script_id` + 玩家字段 user_id/bet/payout/时间），用 `script_id` join 上面的索引 → 每发带上版面属性，再任意聚合：

- `snapshot`（SUPER）取子字段：`"snapshot"."table_id"::varchar`、`"snapshot"."script_id"::varchar`（`snapshot` 是保留字，必须加引号；整体转字符串用 `json_serialize`）。
- BASE spin 的 script_id → BG 剧本；FREE spin → FG 剧本（索引里 `side` 区分）。
- 实测覆盖：近 3 天 SS03，BASE/FREE 打标 **均 100%**。

## 5. 校验口径

- **覆盖率**：join 后未命中的 `script_id` 应极少；若某张表大面积未命中 → 它用了 v2_6 之外的剧本，需拿对应库版本或找后端确认。
- **一对一**：官方 `counts.script_ids_with_more_than_one_record = 0`，即每个 script_id 唯一对一个记录，join 不会放大行数。
- **status**：记录带 `activate/inactivate`，分析时可留意是否只看 activate。

## 6. 老数据（2 月–3/5）的不同（一般不用）

那段 `snapshot.script_id = "1"`（小整数，不是 uuid），另有顶层列 `script_num`（4 月起为 NULL）。要连库得走另一张表 `public.math_mapping_rule`（`game_id, table_type=base/free, script_number → script_uuid`=记录 uuid）。**只在这段用；4 月后一律用 §3 的 `script_id_map.json`。**
